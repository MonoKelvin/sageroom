## 2. 状态和冲突处理

- **原文明确定义**：直接来自初始需求；不因为文档整理而重新变成开放问题。
- **推荐设计**：为落地提出的技术、分期和默认值，尚未被用户批准。
- **待验证**：存在资料或推断，需锁定版本、编译、实机或实际 endpoint 验证。
- **已验证实现**：必须有代码、可复现测试和结果；首批子场景执行记录见 10/11，不能扩展为整体 V1 通过。

冲突时，最新用户明确确认的变更优先；未变更部分以原始需求为先，其次为相应专项文档的合同。本文集中记录确认状态；02 维护需求，04 维护模型决策字段，03 维护应用 IPC，05 维护数据字典。其他文档引用这些合同，不另造同名字段。

文档中的 JSON 和 SQL/接口说明是设计样例，不是可运行实现。附带数据不是思维链，不是任意执行指令。

## 5. 统一参数建议

以下是实现与验证的起点，不是性能、费用或拟人行为保证。**P-TIME-01 是原文硬规则；P-DATA-01/02 已作为首批分页和文本上限批准采用，其他数值仍为待确认建议。** 权限、总预算和大小限制由 Rust 强制；模型只能在这些边界内作语义决定。UI 设计 token 和动画时长单独在 08 维护，性能目标在 10 维护。

### 5.1 调度、请求与动作

| 参数 ID | 建议值 | 规则 |
|---|---|---|
| P-RUN-01 | 事件合并窗口 500ms | 合并观察机会，不是定时轮流发言；高水位不可丢 |
| P-RUN-02 | 全局模型并发 4；每成员社交决策 1 | 摘要、修复及工具后续也占全局名额；提供方可设更低上限 |
| P-RUN-03 | 每次决策最多 12 条消息 | 每条独立提交；首次即产出自然短句，过长时才二次请求拆分 |
| P-RUN-04 | 分条延迟 0～30s，非递减 | 延迟是相对本次验证完成时间；超过窗口拒绝计划 |
| P-RUN-05 | 普通自主检查 5min～24h，最多一个有效检查计划 | 约束模型计划，不自动创建；短期自我回看单独按 P-RUN-10 |
| P-RUN-06 | 无新消息/资料的自主检查最多 2 次/滚动小时 | 超限延后已有模型计划至可用窗口并展示保护；日常跨日问候不永久累加为无信息死锁，不能无计划轮询 |
| P-RUN-07 | 同根自动链最多 20 条；自动消息 12 条/min、120 条/h | 滚动窗口统计；用户发送不重置小时/日预算 |
| P-RUN-08 | 语言模型总请求 500 次/日 | 包含沉默、修复、摘要、任务后续和网络重试；默认固定 UTC 日窗口，UI 显示重置时间 |
| P-RUN-09 | 结构修复最多 1 次；语境竞争重决策连续上限 2 次 | 计入预算；超限保留 pending range 并显示保护，不以无界再入队重置计数 |
| P-RUN-10 | 一次性自我回看在目标消息提交后 1～90s | 每成员仍至多一个计划，绑定本次消息 ordinal；调用及撤回均须在目标有效窗口内，无计划不自动创建 |
| P-NET-01 | 单次语言请求总截止 90s，首次字节 30s，流空闲 30s | 实际模型可单独调整；本地响应不等待网络 |
| P-NET-02 | 可重试请求最多 3 次实际尝试 | 截止时间不随重试无限延长；Retry-After 超过剩余截止时停止 |
| P-NET-03 | 生图创建默认 1 次；远端任务等待最长 10min | 响应丢失先查询/结果未知；poll 次数与搜索额度单独约束 |
| P-TOOL-01 | 同根任务最多 4 次模型步骤、3 个外部工具动作；委托深度最多 2 | 初次/反馈/修复/子委托共享剩余额度，根深度为 0；多个并行调用逐项计数 |
| P-TOOL-02 | 全局工具运行并发 2；队列最多 20 | 语言模型名额和媒体工作池仍另行约束 |
| P-TOOL-03 | 生图 10 张/日；搜索 30 次/日；单次生图默认 1 张 | 未授权不调用；不同计费单位不能混为免费 |
| P-PROFILE-01 | 自主资料修改默认关闭；开启后至少间隔 7 日 | 上限只阻止过频修改，不按时间随机触发修改 |
| P-TIME-01 | `elapsed < 120000ms` 才可撤回 | 原文硬规则，不提供模型或群主修改入口 |

金额预算未设不等于免费或不限额：请求和工具配额始终生效；首次启用前要求确认已知/未知费用。金额估算不能保证服务商最终账单不超出，尤其响应丢失和价格变化时。

### 5.2 上下文与记忆

| 参数 ID | 建议值 | 规则 |
|---|---|---|
| P-CTX-01 | 社交输入预算 6000 tokens，输出上限 1024 tokens | 实际上限取模型容量及成员设置中更严格值；中文/图像不按字符数冒充准确 tokens |
| P-CTX-02 | 近期消息目标 30 条，最多 80 条 | 限制是目标，不保证全部放入；被提及及引用优先于无关旧文 |
| P-CTX-03 | 群摘要目标 1200 tokens；独立记忆最多 8 项、1200 tokens | 两类均纳入总输入；不足时先缩减低相关可选内容 |
| P-CTX-04 | 未归纳有效消息累计 80 条或 12000 估算 tokens | 触发一次有预算的候选压缩任务，模型决定话题分段 |
| P-CTX-05 | 有新增未归纳记录且距成功归纳超过 24h | 仅应用运行时检查；无新增不调用，睡眠不补跑每个 tick |
| P-CTX-06 | 历史检索每次最多 20 个候选，最终召回最多 8 项 | 候选检索不强制写入上下文；embedding 默认关闭 |
| P-CTX-07 | 单条记忆最多 1000 Unicode 字符 | 来源、类型、范围、有效期独立字段；不把大段聊天塞入记忆 |

### 5.3 本地数据、媒体与诊断

| 参数 ID | 建议值 | 规则 |
|---|---|---|
| P-DATA-01 | 分页默认 50，上限 200 | before/after/around keyset；搜索与导出另行流式处理 |
| P-DATA-02 | 文本消息最多 10000 Unicode 字符、32KiB UTF-8；每消息 9 个附件 | 两种限制同时检查；智能体输出还受 token 和动作限制 |
| P-MEDIA-01 | 图片/表情单项 20MiB；普通文件 100MiB | 从实际流量检查，不只看扩展名或声明 |
| P-MEDIA-02 | 静态图片最多 2000 万像素；GIF 最多 200 帧、累计 1 亿像素 | 解码前尽量读尺寸，解码过程中限制累计成本；压缩字节小不等于安全 |
| P-MEDIA-03 | 媒体阻塞工作池同时最多 2 项，单工作估算解码内存 256MiB | 与全进程目标共同验证；不得先全量解码再检查 |
| P-MEDIA-04 | 附件软上限 5GiB；缩略图/临时缓存上限 256MiB | 软上限提示并阻止超出策略的新增，不静默删原附件 |
| P-IMPORT-01 | 恢复包实际展开总量 10GiB、最多 50000 条目；单项最大 2GiB | 数据库与普通附件使用不同校验；大库需显式提高维护上限 |
| P-IMPORT-02 | 新 staging 保留最多 24h | 只清理应用创建且无活动操作引用的暂存；不删除外部源文件 |
| P-LOG-01 | 脱敏诊断轮转：每文件 5MiB，最多 10 份，最长 14 日 | 详细日志需临时授权，默认不含正文、提示词和思维链 |
| P-SKILL-01 | 每成员 SKILL 最多 64KiB UTF-8 | 仍计入上下文预算；不能因文件允许 64KiB 就保证可全部发送 |

`MiB/GiB` 为二进制单位。修改安全上限仅允许本地用户操作；数值调整不是自动删除授权。网络网页/下载上限详见 09，性能测量门槛详见 10。

### 6.1 v0.3 整体复核结论

已对照原始需求复核全部 13 份文档，修正其余 12 份；原文保持不变。主要问题不是缺少需求编号，而是部分合同无法形成执行闭环。以下修正仍为设计，未被冒充为应用验证。

| 原问题 | 本轮修正 | 主要落点 |
|---|---|---|
