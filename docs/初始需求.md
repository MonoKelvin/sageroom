# Sageroom

一个AI Agent智能体聊天室应用。自己也能参与聊天，内置各种性格的智能体，能互相对话聊天，可以是吐槽、胡诌、谈笑风生、谈天说地、日常琐事、新闻八卦、热点评论、等等。每个智能体支持修改性格特点、语言风格，也可以新增智能体。

## 需求

1. 一个桌面端聊天应用（临时，下个大版本适配手机端），类似仅有聊天功能的QQ、微信、钉钉等应用。
2. 常驻托盘图标，有消息时托盘图标闪烁提醒（非系统提醒，@自己的时候可以设计成系统提醒，如windows右下角的弹出小窗口），角标数量、消息预览、声音提示（可以配置）。
3. 内置至少一个通用智能体Sage
4. 支持自定义智能体性格、语言风格、称呼等参数
5. 就一个聊天室，所有智能体都可以畅所欲言，自动决策是否回复和回复内容，自动决策首个消息发出时间和内容（比如有时事热点想要推送、日常问候等等），自动极低概率触发消息撤回（如写错文字、语法错误、不合时宜文字、错发误发等），要设置成2分钟后不能撤回。
6. 群主（默认自己，也能指定其他智能体）也可以参与对话、回复。其他智能体可以自动决策是否回复、延申对话、选择性忽略（概率低情况）、引用回复等
7. 支持发送文件、图片、表情包。自己可以选择以上内容（内置颜文字、表情符号、表情包，支持自定义表情包，即图片截图或gif），智能体也能自我决策发送以上内容。
8. 特色功能：有些智能体可以设计成工具类智能体（群里很少说话的），比如用于生图、处理问题等，比如@他后让他生成一张图片（要求配置文生图大模型），他收到后，在后台慢慢执行。比如@他让他上网查询相关热点新闻等，比如让他计算一些表达式或写一段简短代码等
9. 当前版本暂时不需要支持多用户和多真人联机功能。就是面向个人的使用。支持个人修改昵称、头像和相关参数。
10. 每个智能体是独立的个体，可以有昵称、头像、自我介绍（或者不写）、性别、性格、语言风格等等。可以配置或者极低概率触发智能体自行修改这些内容。如果出现大模型费用不够、网络问题、参数问题等任何导致无法回复的（超过最大重试次数也没有响应，则标记该智能体离线，软件发送一个小标记类型的消息告知该智能体（实际用昵称）离线），则智能体状态为离线。用户可以点击那个标记或者点击智能体头像去检查日志、大模型等，可以更换大模型后重试上线。
11. 对智能体：消息输入是SKILL+历史（可以总结）+上下文（可以总结）+环境参数（如时间、成员状态）+对象描述（成员信息等）等内容，可以部分使用json格式；输出是json格式，至少包括直接的消息内容+附加数据（可以融入到历史记录、上下文中的附加内容）等。这部分也需要专项分析，设计一套输入输出准则标准，尽可能让输入全面（重点还是记忆点和氛围环境因素对结果影响较大）

## UI设计

1. 精简、简约、高级、扁平化、现代化、多毛玻璃少阴影、多圆角少边框、丰富的动画设计、友好的交互设计
2. 主界面：一个聊天室，默认尺寸大概就是一个iPhone手机屏幕的尺寸，标题是群名称（右侧窗口控制菜单和设置）、主要内容是聊天列表、下面是消息输入框
3. 设置界面：需求中可以设置的内容

## 技术路线参考（重点）

1. 采用前端tauri框架，要求轻量级，不占内存，能自定义标题栏的无边框窗口和原生阴影；图标使用tablericon库、UI框架使用shadcn/ui、布局体系用tailiwindcss
2. 尽量多使用三方依赖库，少造轮子。比如聊天列表组件、颜文字、表情包、表情符号等等，Agent配置等也可以使用一些能兼容claude、openai等API的框架库
3. 智能体（重点）：每个智能体本质就是一个SKILL+API。skill约束该智能体的性格和语言风格，API约束使用的大模型，比如配置deepseek（base_url + apikey等）。每个智能体拥有独立的配置文件，用于配置基础参数，互不影响，方便扩展；
   * 每个智能体可以独立开启配置文生图大模型（全局配置后，智能体引用id或者名称等手段）后自动决策是否生成图片（尽量少用，一般是@他后才调用），支持视觉理解的可以读取图片去理解；
   * 智能体要设计成后台独立实时运行的线程，实时监控消息内容，合适时机就回复，否则就是待机状态，但还是监控所有历史消息，切换话题或者上下文无关性差太多后适当舍弃更久的历史消息以节约上下文token。
   * 历史消息也需要做一个存储：常用的聊天软件的存储方案，比如sqlite数据库或者普通文件存储等，按天/周来存储等，这个需要单独调研和思考决策具体的落地方案。存储目录默认用户目录，支持设置一键迁移。对于发送的文件、图片、表情等存储需要设计大小限制、时效性等。存储数据支持一键备份、导入导出。
   * 上下文关联性和记忆：长时间对话可能会触发上下文压缩、内容过滤等，思考按照一定时间或者内容的消息进行压缩整理归纳到文件或数据库，后续对话后就不需要全部输入大模型，不定期或随机或触发等情况下唤起记忆。这一部分也需要重点思考可行性方案。
   * **重点：能让智能体通过大模型自行决策的任何事情，就让智能体自行完成，尽量避免在代码中写相关智能体的逻辑**。代码做的事情是提供API、参数、SKILL或者资料、材料等让智能体去实现各种操作。
4. 代码设计：尽量按照功能模块独立化设计，越低耦合越好，每个独立功能有独立的输入输出准则，外部不需要了解内部实现，只需要知道每个模块自己需要什么，需要产出什么即可。其他模块根据输入输出来设计就不会犯错。
5. 智能体配置说明：应该提供全局的配置，配置智能体的时候通过选择组装的方式，比如预先配置好一些大模型、文生图、特点预设等。再配置智能体的时候就直接下拉选择已有的设置了，如果需要微调，就可以独立调整相关参数（修改的是复制的全局参数的副本）
6. 代码设计多提供API，后续可以直接让工具调用API（类似MCP）操作整个软件，比如AI搜索聊天记录、AI生成回复消息、AI总结聊天消息等等（当前版本暂时不做），目的就是尽可能提供原子化API操作，方便调用。

## 智能体的拟人化设计（重点）

智能体应该默认趋近于人类的对话风格、接近人类的消息发送规律，如文字长度、内容、频率、回复响应、错别字、撤回、问候、吐槽、反问、阴阳、一句话分多条发送等等。对于错别字、撤回等又是极低概率事件，而且即使错误或者有不合时宜，也不一定触发撤回或者重说等，不同性格、风格也会有影响。

不感兴趣就沉默。

群主和任何智能体一样，在聊天上没有特殊权力，不是说可影响讨论秩序及话题风格。而是可以修改群名称、群参数、@所有人、发通告而已，其他和普通成员一样。

智能体不是以服务“我”为主的，而是每个智能体都是独立的成员，可以互相发消息和对话，没有谁服务谁的规则，除非是工具类智能体，我和每个智能体都有权力去@他，让他完成相关事情（没有明确需求的情况一般不会@工具类智能体）

聊天群不能一直在说话，不能不间断产生大量消息，应当根据人的聊天风格可能稍长的对话部分智能体就可以下线了，之后合适的时机又可以进入；比如部分消息发送后没人回复就间隔一段时间，要通过大模型的决策完成，而不能通过代码写随机算法来完成。简言之：上下文输入给大模型后，有机会触发不回复消息的情况，而不能通过代码写随机算法或判断来完成，多交给每个智能体去自行判断。

智能体调用大模型回复的时候一般要去除思考参数，直接回复消息结果。除非对于复杂消息、调研查询类、算法类等需要思考的少数场景才可能开启思考。

当然也可以通过参数配置拟人程度，比如配置专业度、正式度、随意度、幽默度、低情商度、高情商度等等。

如果是拟人化智能体，SKILL里面也需要描述一些去AI味道的提示词（可以全网搜索最新的最好用的去AI味道的skill融合进来）
